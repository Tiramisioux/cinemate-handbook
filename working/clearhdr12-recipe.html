Making 12-bit ClearHDR work

What the pipeline actually does to companded sensor data, why the preview renders pink, and the ordered configuration that follows from it. Every line is labelled by how well it is known.

01

The verdict

Stop paying for 12-bit ClearHDR, and capture 16-bit with a log encode instead. The sensor's 12-bit mode exists to save link bandwidth and file size. On this rig it saves neither in a way that matters, and it costs a compander whose curve must be measured per binning, a full-frame CPU re-render of every preview frame, and a class of highlight anchor that has now been wrong three times.

Make 16-bit ClearHDR with --log-encode 12 the default capture, and keep 12-bit as an opt-in compatibility mode for older kernels and unpatched mono rigs. The one gate before committing is sustained write throughput, which nobody has measured for this combination.

The third figure is the real argument. Both encodings put a 16-bit linear signal into 12 bits. The sensor's compander spends 172 codes on the range from 500 to 11500 in linear units, at 64 units per code. CineMate's own log curve spends 1378 codes on the same range, between 2 and 26 units per code. Where the picture lives, the log curve is between 4 and 32 times finer. The compander is finer only above roughly 15000, which is the region the merge clamp flattens anyway.

One caution about the file-size figure. It is not a reason to expect relief on the write stream either way: with the thumbnail a live take was seen to carry, both depths land near 330 MB/s at 4K and 25 frames per second, within a couple of percent of each other.

02

What the camera said afterwards

This page was written from code and archived measurements. It was then used as the brief for a night of work at the camera, and several of its claims did not survive contact. The hardware log is the record; this section says only what changed and why, so nothing here quietly disagrees with it.

12-bit ClearHDR now passes. The operator's verdict after the final build was that it looked good, which is the first unqualified pass any ClearHDR mode has had in this investigation. It came from letting the 12-bit path anchor on its own per-frame measurement instead of a table constant, not from anything done to the preview's appearance.

The root cause nobody had found

The artefacts that reverted this work twice came from a bug this page did not spot. The rule that decides whether a highlight is clamped was corrected months ago to compare the second-brightest channel against the brightest, because a tungsten bulb pins two channels and leaves the third low. That correction was applied to the trigger and never to the detector that measures where the clamp sits. So on a tungsten subject the detector reported nothing clamped, the 12-bit path fell back to a constant measured under quite different conditions, and the correction whitened a third of the frame with a noisy rim. Feathering that rim was treating the symptom, which is why it was reverted after it worked.

Teaching the detector the same rule the trigger already used took the whitened area from 33.7% of the frame to 9.5% and produced the operator's pass.

And the thing none of it fixes

Above the gain window the merge stops at 55 to 59 percent of the container, so a blown highlight has no roll-off for any renderer to show. Switching the same lamp to the non-HDR mode drew an unprompted "now it looks nice" from the operator. Correcting the preview can only choose what colour a flat plateau is painted. That is why the remaining fix is a constraint in the camera's ISO list rather than anything in the preview code.

03

What happens to the data

The defect is not a bug in one function. It is a domain mismatch that survives every stage: the sensor compresses its own tone curve into 12 bits, and nothing downstream is told. The image signal processor reads companded codes as if they were linear, which crushes the mid-tones toward magenta, and white balance then drives the clamped highlights pink.

Why the highlights go pink

When the merge clamps, it clamps digitally, and the colour channels converge on one code as it does. A blown area therefore arrives with two or three channels sitting on the same number. White balance then multiplies red by 1.8 and blue by 1.7 into clipping while green, already at the ceiling, cannot move. The result is pink, in the preview, the web view and the embedded thumbnail alike.

This is why the correction can only key on the channels agreeing, never on the level they agree at or on the resulting hue. A genuinely white subject was measured at the same level as a clamped one in the same frame; only the ratio between the brightest and second-brightest channel separated them, 0.659 against 0.998.

The finding that reorders this list

The pink in a blown 12-bit highlight is not caused by the compander. It is the same mechanism as in 16-bit, where no compander exists: the channels converge, white balance and the colour matrix then drive the result off neutral. The constant-offset identity above proves it, because a constant offset cannot change the ratios between channels once black is subtracted.

That matters for what gets built. The full-frame CPU re-render was introduced for the crushed mid-tones, and it is the right tool for those. It is not needed for the blown highlights, which the far cheaper in-place correction already written for 16-bit should handle unchanged. Try that before optimising a render that may not need to run at all.

05

Rolling shutter

Nothing in the camera's documentation mentions rolling shutter, and ClearHDR changes it in a way that is currently unquantified. The sensor doubles the frame length when ClearHDR is on, at an unchanged line period. Whether that extra time is readout or blanking decides whether the skew doubles, and no source in any of the four drivers says which.

ConfigurationLine periodIf one row per lineIf two lines per row
SDR 4K, fastest link6.36 µs13.7 ms—
ClearHDR 4K, 1782 Mbps/lane7.41 µs16.0 ms32.0 ms
ClearHDR 4K, 1440 Mbps/lane8.89 µs19.2 ms38.4 ms
ClearHDR HD, binned7.41 µs16.0 ms32.0 ms

Three consequences hold whichever reading is right. The binned HD mode gives no relief, because the sensor bins after readout and still reads all 2160 rows; the driver says the readout speed is the same as 4K and the two modes share a frame length. Shooting slower does not help either: dropping from 30 to 25 frames per second adds vertical blanking and leaves the readout untouched. A faster link does help, because it shortens the line period, but ClearHDR floors that line period well above what the sensor allows in ordinary modes, so the best skew available in ClearHDR is worse than the best available outside it.

The measurement is cheap and decisive, and it settles the bandwidth question at the same time. Point the camera at a mains-powered LED, which flickers at twice the mains frequency, and count the pitch of the horizontal bands in the raw frame. At the current operating point, 100 Hz flicker gives bands 1350 rows apart if the sensor reads one row per line period, and 675 rows apart if it takes two. There is no ambiguity between those two answers.

The merge clamp

Three shipped builds anchored the highlight correction on a raw code, and all three were wrong, because the code is not a sensor property. It moves with analogue gain, with the blend setting and with the scene.

12-bit HD, gain code 802 392 – 2 6520.538 – 0.601The binned mode sits lower, and nobody knows why

The working model is that below the selection threshold the output follows the high-gain read, and above its saturation it follows the low-gain read scaled by an alignment factor. The ceiling is that scaled maximum. What is not known is whether the factor tracks the gain adder, whether the blend weights enter it, and whether the fall with analogue gain is a hard limit at the documented 29.1 dB sum or a continuous loss.

This has since been measured, and it reframes everything above. The application note bounds the sum of sensor gain and the gain adder to between 9.6 and 29.1 dB. The sensor runs the adder at 12 dB, which caps usable gain around code 57. Swept on the camera with each gain write confirmed in the journal, the merge uses the entire container below that and collapses progressively above it. So the plateau is not a property that moves; it is the merge failing, and the numbers this page and the hardware log have been chasing for a week are all points on that one curve.

07

The recipe

Apply top to bottom. A line marked unknown must not ship before the measurement named beside it. Several lines here have since been worked at the camera: the preview instrumentation and cost cuts landed, the detector now measures the clamp with the same rule the trigger uses, and 12-bit passed the operator. The ISO constraint below is the substantial one still unwritten.

Sensor imx585 driver, cinemate-7modes

  1. 1.1confirmedLeave the ClearHDR register set alone. WDMODE 0x10, COMBI_EN 0x02, thresholds 0x0FFF and 0, compander slopes 1/64 and 1/16, knees 500 and 11500. Do not touch the unnamed ClearHDR writes; nobody knows what they do.
  2. 1.2confirmedBlend stays at index 5. The low indices carry the speckle and flat-pedestal defects that cost a week in August.
  3. 1.3confirmedKeep the sum of sensor gain and the gain adder inside 9.6 to 29.1 dB. Measured on the camera, that is ISO 200 to 799. Implement as an ISO limit in CineMate, not a driver change, and prefer a constraint to a warning: nothing in the preview tells an operator the mode has quietly stopped being an HDR mode.
  4. 1.4unknownDo not move the compander knees onto the hardware curve's grid unless the front-end path is chosen and its output domain settled. Both knee anchors would need re-measuring per mode.

Image pipeline libcamera fork, branch cinemate

  1. 2.1confirmedFor the recommended path, change nothing. Keep the byte-swap exemption for compressed buffers and the single black level of 3200.
  2. 2.2confirmedOnly if the front-end path is pursued: cherry-pick the four upstream decompand commits. They apply with exactly one conflict, in the front-end lock block. Do not rebase onto upstream; a later commit there breaks this fork's 16-bit packing map.
  3. 2.3confirmedOnly for that path: select the curve on frame width, never on the binning fields. This driver reports binning as 1 in every mode, so the obvious gate silently never fires.
  4. 2.4unknownOnly for that path: confirm the recorded buffer is taken after the decompand block before any tuning file becomes default. Capture one frame with the block on and one with it off, and compare the low four bits of each sample.

Capture cinepi-raw

  1. 3.1confirmedRe-land the reverted preview branch. Without it, 16-bit previews render pink below roughly ISO 1585. This is the prerequisite for everything else.
  2. 3.2probableGate the trigger in integers and skip the write where the blend is zero. Measured byte-identical on x86 at less than half the cost; verify byte-identity on the Pi with one frame before merging.
  3. 3.3confirmedKeep the 12-bit path for the opt-in mode, and measure its binned anchor from a take at a recorded gain instead of deriving it. Before optimising its full-frame render, try the 16-bit in-place correction on 12-bit: the blown-highlight defect is the same mechanism in both depths.
  4. 3.4probableOptionally crop the discarded rows when writing 16-bit files: 20 at the top and 20 at the bottom, centred, since the sensor prepends optical black and appends over-read. Cropping 40 from the top would shift every frame down. Done right it makes the log-encoded file slightly smaller than today's.
  5. 3.5confirmedFix two stale statements in the README: the 16-bit frame-rate ceiling, and the description of the gain adder's path through the sensor.

Camera CineMate settings and Redis defaults

  1. 4.1probableMove the boot default to the 16-bit modes. The encode resolver already maps 16-bit sources to log-12. Leave the 12-bit entries enabled: disabling them renumbers every ClearHDR mode, and the selected mode persists in Redis across boots, so a saved setting would silently become a different capture.
  2. 4.2confirmedTurn the log encode on. It ships off for both cameras. Without this change the new default writes 490 MB/s instead of 385, which is the difference between a plausible take and a stall.
  3. 4.3confirmedHold the blend and gain-adder defaults until the sweeps below say otherwise.
  4. 4.4confirmedCap the ClearHDR ISO list at 799, the last value inside the sensor's combination window. Keep the 800 step selectable and land it there, tinted green, so the control stays where the operator expects and the colour says the camera is holding it. Drop 1200 and above: at 1200 the merge has already begun to collapse and by 1600 it has lost about a stop and a half of highlight range, which is what the mode was turned on to capture. Built and confirmed live on the feature branch; dev still carries an earlier 1585 ceiling that this supersedes.
  5. 4.5confirmedSwitch the thumbnail to JPEG. The camera currently seeds the full preview plane uncompressed, 2.7 MB on every frame, which is roughly a fifth of the file and the single largest lever on write throughput. The JPEG mode is already implemented and costs about 5 KB.
  6. 4.6probableRecord the analogue gain code with every ClearHDR take. Every plateau number in the project's history that lacks one is why the clamp model still has free hypotheses.
08

What to measure, and what each outcome means

In order. The first two gate the recommendation; the rest close the clamp model.

  1. Does a ten-minute 4K take at 25 fps sustain without dropping frames, in both depths? Run it twice, once per depth, same length and same thumbnail, or the result cannot be attributed. Today's default writes 380 MB/s and the recommendation 385, while this rig has stalled at 355. A failure would indict the current default as much as the new one. The cheapest fix if it fails is the JPEG thumbnail, which takes both to about 315 MB/s.
  2. Does the sensor read one row per line period in ClearHDR, or two? Shoot a mains-powered LED and count the band pitch. Prediction: 1350 rows apart means one row per line and a 16 ms skew; 675 rows apart means two and a 32 ms skew. The same answer settles whether 16-bit fits the link at the current rate.
  3. What does each per-frame stage actually cost on the Pi? Time the preview render, the in-place correction and the byte-swap, and log them beside the dropped-frame count. Prediction: the 12-bit render lands between 20 and 40 ms against a 40 ms budget, which would make it the cause of the frame drops that reverted the branch. Only x86 figures exist today.
  4. Do the blend and gain-adder writes reach the sensor at all? One register read while streaming. A write has been seen to report success while the control still read its old value, and the driver rewrites the adder at every stream start. Until this is done, every plateau number rests on an assumption about what the sensor was set to.
  5. Does the plateau fall in one step at the documented gain bound, or continuously? Sweep ISO 200 to 1600 with the gain code logged. Prediction if it is a hard bound: unchanged through code 76, then a drop of about a tenth at code 80. If continuous: a steady fall of roughly 0.37 dB per dB of gain across the whole sweep.
  6. Does the blend setting move the plateau? Four takes at indices 0, 3, 4 and 5. Two of those indices are documented as the same weighting and differ only in one bit, which tests whether the old speckle defect was the weighting or the index. No numeric expectation exists — this one is genuinely open.
  7. Are the ragged edge pixels exact ties, or merely close? Run the supplied probe on the tungsten take. Prediction: genuinely near-equal rather than tied, which would mean a tolerance in code space cannot help and the matte must be feathered instead.
09

If a vendor recipe can be obtained

These are the questions whose answers would turn the experiments above into confirmations. Ask for register-level statements for the sensor in built-in combination mode, at both output depths.

  1. The merge formula: how the combined output is formed from the two reads as a function of the thresholds, the blend weights and the gain adder, including where the black pedestal enters and what sets the ceiling.
  2. Which read the gain adder scales, and whether the high-gain path carries a fixed conversion-gain step in this mode.
  3. What happens when the gain sum leaves the documented 9.6 to 29.1 dB window: a validity limit, a clip, or undefined.
  4. Whether the sensor clips or wraps when the aligned value exceeds the 16-bit container. One vendor's own driver warns that bright areas can render black, and nobody has explained it.
  5. Why the binned plateau sits lower, and whether 12-bit compressed output in the binned mode is supported at all. Two drivers read the application note as saying it is not, while this camera records usable data from it.
  6. The exact knee placement in stored codes, since the measured curve sits a fraction of a code above the register value, and whether the second knee carries the same offset.
  7. How many line periods one merged output row occupies on the link, which would turn the bandwidth question from inference into arithmetic.
  8. The function of the ClearHDR-only registers no public driver names, and whether any of them sets an output ceiling.

For the Raspberry Pi side, three questions would remove the front-end path's remaining unknowns: whether the recorded output is taken after the decompand block, how the hardware interpolates between the 65 curve points, and whether the black-level block clamps values below black when its input and output levels are equal.

Confidence labels follow this project's own rule: a diagnostic that cannot come out wrong is not evidence. Three of the four wrong turns in this investigation came from reasoning past the evidence rather than from bad measurement, which is why every unknown here names its measurement instead of an argument.
